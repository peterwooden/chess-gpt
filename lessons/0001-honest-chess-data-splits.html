Split games, not positions.

A validation score is useful only when it measures the kind of novelty we claim it measures.

Start with a prediction

Suppose we expand every game into many overlapping next-move examples, shuffle those positions, and then split them. Positions from one game can now land in both training and validation.

Why the unit matters

e4 e5 → Nf3→ One envelopeall train or all validation

The examples share moves and prefixes. If we scatter them across splits, validation can reward recognition of a game already represented in training. That is data leakage.

Choose the implementation

A · Take the last 10% of rows. Keeps each game intact, but the result depends on file order and may inherit chronology or source bias.

cut = round(len(games) * 0.9)
train, validation = games[:cut], games[cut:]

B · Shuffle positions after expansion. Looks random, but examples from the same game can cross the boundary.

examples = expand_to_positions(games)
shuffle(examples)
train, validation = split(examples, 0.9)

C · Hash a stable game identity. The whole game follows one deterministic assignment independent of row order.

digest = blake2b(f"{seed}:{game.site}".encode(), digest_size=8).digest()
bucket = int.from_bytes(digest) % 100
split = "validation" if bucket < 10 else "train"
